# Профилирование интерфейса

Проверены набор текста, прокрутка колонки, поиск и переключение заметок в Chrome на Windows.
Изменения редактора, списков и репозитория общие для веба и Tauri. Отдельные замеры в установленном
WebView2 и WKWebView пока не выполнены.

В первоначальном сравнении 150 искусственных заметок, 120 карточек загружены после прокрутки. Длинная заметка — около
116 тысяч символов и 4000 абзацев. Исходная версия — `af39231`, в отдельном временном checkout.
Каждый прогон использует новый профиль браузера, без доступа к личным заметкам и аккаунту.
Таблица показывает по одному прогону Vite dev server; это ориентир для регрессий, а не замер
производительности релизного приложения. Набор включает 15 мс задержки между клавишами.

| Сценарий | До | После |
| --- | ---: | ---: |
| Набор 48 символов | 2289 мс | 1562 мс |
| Сериализаций Markdown во время набора | 49 | 0 |
| Сериализаций к завершению сохранения | 49 | 1 |
| Время сериализации за этот сценарий | 380 мс | 14 мс |
| Ввод поиска и появление результатов | 777 мс | 422 мс |
| Четыре переключения коротких заметок | 814 мс | 394 мс |
| Длинных задач при переключениях (>50 мс) | 5 | 0 |

Прогон также прокручивает колонку. После изменений в dev-сборке остаются отдельные длинные задачи
при сохранении, поиске и загрузке следующих страниц: работа не объявляется полностью свободной от
задержек. Первое открытие длинной заметки не входит во время четырёх переключений.

Что изменилось:

- Редактор хранит неизменяемый снимок ProseMirror, сериализует его при сохранении, blur и уходе.
  Проверены все чтения `latest`, включая совместное редактирование и `onLeave`. Очередь сохранений
  защищает новую правку от ответа предыдущей медленной записи. `shouldRerenderOnTransaction: false`
  оставляет подписки тулбаров через `useEditorState`.
- React Compiler включён для React-кода веб-приложения и UI-пакетов. На карточках дополнительно
  стоит `memo`: компилятор может пропустить функции с ref в обработчиках жестов. В профиле была
  заметна стоимость создания `Intl.DateTimeFormat`; форматтеры теперь используются повторно.
- Полная виртуализация через `@tanstack/react-virtual` заменила промежуточный вариант с
  `content-visibility`. Колонка, её поиск, сетка и оба списка монтируют видимые строки с запасом.
  Высоты измеряются, сетка виртуализируется рядами по 1/2/3 карточки. Строка с фокусом,
  контекстным меню или источником перетаскивания остаётся смонтированной. Выделение хранится
  вне карточек; Home/End и стрелки переходят к ещё не смонтированной строке.
- После сохранения `cacheSavedNote` подставляет ответ репозитория в карточку и открытый документ.
  Курсоры сохраняют границы прочитанного диапазона, учитываются фильтры и порядок сортировки.
  Остальные карточки сохраняют прежние объекты. Поиск перечитывается для подходящих списков,
  навигация — при изменении её счётчиков. При создании конфликтной копии выполняется прежнее
  полное обновление. Обычная правка абзаца не перечитывает списки и навигацию.
  Запись в БД, запуск облачного синка, индексация и `shared.live.persist()` сохранены.
  Входящие удалённые изменения обновляют UI прежним путём; инвалидированный неактивный кэш
  остаётся устаревшим после подстановки одной карточки.
- Снимок навигации обновляется через `useDeferredValue`. Сам Zustand обновляется сразу; обёртка
  `startTransition` вокруг записи во внешний store не решила бы задачу. Поиск в колонке и Spotlight
  уже использовал `useDeferredValue`.
- Папки и счётчики читаются одним запросом `NotesRepo.navigation`, который делят `useFolders` и
  `useCounts`. На Tauri это один вызов `db_query` вместо двух. Тест проверяет один SQL-вызов,
  пустую библиотеку, удаление папки, счётчики и наследование доступа общей папки.

Дополнительная браузерная проверка использует 1000 заметок, одну закреплённую. После загрузки
всех страниц в DOM было 14 карточек в колонке, 36 в сетке, 16 в списке, 29 в компактном виде.
Поиск из 50 результатов монтировал 15 карточек. Проверены ширины 1440/800/500 px, сохранность
выделения после размонтирования и контекстное меню при прокрутке. После сохранения абзаца —
0 вызовов `listNotes` и 0 `navigation`; текст проверен чтением БД. Число смонтированных карточек
зависит от их высоты, окна и запаса строк.

Отдельный `profile:links` измеряет настоящий `LinkCards` на транзакциях ProseMirror. Создаётся
изолированное состояние с тем же плагином и схемой, без сети, DOM и React. Протокол view
имитируется, чтобы ответы загрузчика действительно обновили декорации до начала набора.
В каждом случае 50 прогревочных и 200 измеряемых вставок в последний обычный абзац. Есть сценарии
с полученными превью и с запасными карточками, когда загрузчик не вернул метаданные.

Повторное сравнение исходного плагина (`77e02f1`, blob в Git) с инкрементальной версией:

| Абзацы / карточки ссылок | Среднее до | Среднее после | p95 до → после |
| --- | ---: | ---: | ---: |
| 1000 / 20, превью в кэше | 0,224 мс | 0,014 мс | 0,3 → 0,1 мс |
| 1000 / 200, превью в кэше | 0,934 мс | 0,106 мс | 1,1 → 0,2 мс |
| 4000 / 0 | 0,613 мс | 0,038 мс | 0,8 → 0,1 мс |
| 4000 / 20, превью в кэше | 0,792 мс | 0,038 мс | 0,9 → 0,1 мс |
| 4000 / 200, превью в кэше | 3,264 мс | 0,131 мс | 3,4 → 0,2 мс |
| 4000 / 200, запасные карточки | 3,542 мс | 0,153 мс | 4,0 → 0,2 мс |

На тяжёлом сценарии средняя стоимость плагина снизилась примерно в 25 раз: около 3,13 мс
освободилось на одну правку. Это не ускорение всего редактора в 25 раз. Таймер браузера имеет
шаг около 0,1 мс, поэтому для маленьких значений показано среднее серии, а не нулевая медиана.
Результаты — `link-cards-before-incremental.json` и `link-cards-incremental.json` в `.cache/profile-ui`.

Теперь существующий DecorationSet переносится через mapping транзакции; заново строятся декорации
затронутых верхнеуровневых блоков и соседей на границах. Диапазоны всех шагов приводятся к финальным
позициям, объединяются; шаги изменения marks/атрибутов с пустой StepMap сравнивают свои документы.
Распознавание ссылки читает узлы ProseMirror напрямую, без `toJSON()` для каждого абзаца.
Ответ загрузчика и повторная загрузка меняют только карточки соответствующего URL, включая его
повторные вхождения. Остальные виджеты сохраняют своё оформление и DOM. Инициализация или замена
всего документа по-прежнему требует обработки всех его блоков.

Измерение считает работу состояния плагина без создания DOM и отрисовки. Отдельно браузерный
`test:links` с настоящим EditorView проверяет сохранение DOM-узлов при наборе, обновление повторных
ссылок, удаление, поздние ответы, undo/redo, замену документа, retry, `plainLink` и открытие карточки.
10 unit-тестов включают 250 смешанных изменений с проверкой результата по полному сканированию.

Плавность при 165 Гц не подтверждена: headless Chrome и dev-сборка не заменяют измерения FPS,
p95/p99 кадров и задержки ввода в релизном WebView2 на самом мониторе. Первый разбор большой
заметки и фоновые задачи ещё могут пропускать кадры.

При проверке синхронизации обнаружен отдельный тяжёлый случай `node-diff3`: добавление строк в
начало и конец длинной заметки с тысячами одинаковых абзацев. Исходный тест пришлось прерывать
после длительной блокировки. Теперь раздельные изменения объединяются линейно, общий контекст
обрезается перед diff, а стоимость неоднозначного LCS ограничена до его запуска. При превышении
лимита трёхстороннее слияние сохраняет конфликтную копию. При объединении дневных заметок обе
сложные части сохраняются целиком; в этом редком случае возможны повторяющиеся строки.

Медианы пяти замеров вспомогательных операций на синтетическом тексте 124011 символов:

| Операция в главном потоке | Время |
| --- | ---: |
| Хэш и разбиение для индекса | 7,6 мс |
| Слияние изменений в начале и конце | 0,8 мс |
| Шифрование и расшифрование | 2,9 мс |

Эмбеддинги уже вычисляются в worker. Оркестратор индексации берёт по восемь заметок и уступает
поток между пачками; SQL на вебе выполняется в worker, на десктопе — в Rust. Эти отдельные замеры
не заменяют профиль полной синхронизации библиотеки и первого Markdown-разбора в нативных webview.

Для повторения нужен установленный Google Chrome. Из корня репозитория:

```sh
corepack pnpm --filter @fixnote/web dev
# В другом терминале:
corepack pnpm profile:ui --label after --url http://localhost:5173
corepack pnpm profile:core
corepack pnpm test:editor
corepack pnpm test:lists
corepack pnpm profile:links
corepack pnpm test:links
```

`profile:ui` сохраняет результаты, снимок экрана и `.cpuprofile` в `.cache/profile-ui/<label>`.
CPU-профиль можно открыть в Chrome DevTools. `profile:core` сохраняет отдельный `core.json`.
`profile:links` сохраняет `link-cards.json` в `.cache/profile-ui`.
Браузерные проверки сохранения охватывают паузу, blur, уход из заметки, повторное открытие и две
перекрывающиеся медленные записи. Тесты слияния проверяют длинные повторяющиеся тексты, обычные
конфликты, совместимость коротких правок и сохранность обеих полных версий.

Проверки: сборка веба, TypeScript изменённых пакетов, все тесты монорепозитория и Biome изменённых
файлов прошли. Общий `pnpm lint` сообщает существующие ошибки за пределами этих изменений
(в том числе форматирование CRLF); массовое форматирование репозитория не выполнялось.

Защита от утечки через картинки AI в эти изменения не входит: решение отложено для отдельного
исследования. До её завершения ограничение на публикацию раздела про prompt injection сохраняется.
